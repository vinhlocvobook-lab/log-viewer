# Log Viewer Architecture 🏗️

This document describes the high-level design and data flow of the Log Viewer system.

## Overview
The Log Viewer serves as a multi-session observability layer for the DevFriend AI Assistant. It aggregates three distinct data sources into a unified, searchable, and visual dashboard.

## Data Sources
1.  **Project Audit Log:** A human-readable Markdown file (`PROJECT_LOG.md`) where the AI records major milestones and decisions.
2.  **Raw Session Logs:** JSONL files generated by OpenClaw containing the exact prompts, responses, and tool calls for each session.
3.  **Session Metadata:** A central `sessions.json` file tracking token usage, model information, and active session paths.

## System Components

### 1. Multi-Session Sync Engine
Instead of focusing on a single file, the server implements a **Multi-Session Sync Engine**:
- It runs a background interval (every 15-30s).
- **Session Discovery:** It scans `sessions.json` to find all active sessions and their associated `.jsonl` file paths.
- **Table Partitioning:** Log entries are stored in the SQLite database with a `session_id` column, allowing the UI to partition data by session.
- **Incremental Sync:** The engine uses file offsets per session to only read new data, ensuring high performance even with multiple background workers.

### 2. SQLite Database (`logs.db`)
- **Table: `project_logs`** - Stores the full content of the audit Markdown.
- **Table: `sessions`** - Catalog of all discovered sessions with labels and last update times.
- **Table: `llm_interactions`** - Stores individual message turns with `session_id` and `content_json` columns.
- **Table: `usage_history`** - Time-series data for main session token consumption.
- **Table: `sync_state`** - Keeps track of file offsets per session file for incremental syncing.

### 3. REST API
- `GET /api/sessions`: Returns a list of all synced sessions.
- `GET /api/logs/llm?sid=<id>&q=keyword`: Returns rich structured data for a specific session.
- `GET /api/logs/usage`: Returns main session metadata, system prompt, and historical usage.

### 4. Frontend
- Built with **Vanilla JS**, **Tailwind CSS**, and **Chart.js**.
- **Multi-Session Sidebar:** Allows switching between the main chat and background sub-agents.
- **Visual Coding:** High-contrast styles for Requests, Responses, Tool execution, and System events.
- **Live Search:** Context-aware filtering within the selected session.

## Deployment Strategy
The app is designed to run alongside the main application:
- **Process Manager:** PM2 ensures the Node server is always up.
- **Security:** Apache acts as a reverse proxy. API access is gated by an `X-Access-Key` header.
